## R - Race conditions e sincronizzazione

Audit del 2026-10-25 su tutto il backend concorrente (subagente con
ricerca sistematica; i finding principali verificati a mano voce per
voce). La suite NON copre oggi: events.py (zero test), rientranza del
backup scheduler, restore-vs-festa-viva, record_cash_count, carrello in
sessione concorrente. Ogni fix R porta con se un test mirato.

### R-HIGH - fix subito (persi dati, blocchi, buchi auth)

- [x] R1  app/services/backup_service.py:217-229 - restore_party_db
  sostituisce il DB di una festa viva senza guardia open_count (a
  differenza di delete_party). copyfile sopra fd aperti + unlink di
  -wal/-shm = vendite recenti (nella WAL) perdite di colpo.
  Fix: guardia open_count(dst) == 0 dentro _lifecycle_lock (rifutata se
  ci sono connessioni vive), come delete_party, + mark_deleting per lo
  span del restore.
- [x] R2  app/services/party_service.py:245-247 (create_empty; idem
  template :69 e duplicate :282-286) - i creatori rimuovono il file di
  una festa esistente senza guardia open_count: se il nome sanificato
  coincide con una festa attiva, le connessioni vive scrivono su un file
  unlinkato = vendite perse in silenzio. Fix: stessa guardia di
  delete_party prima di _remove_db_files.
- [x] R3  app/utils/events.py:95-99 - il generatore SSE fa yield dentro
  "with listener[lock]". Generatore sospeso al yield = lock trattenuto
  finche il socket client non scarica lo chunk: un client lento o
  rotto congela OGNI broadcast() dellapp (checkout compreso) e, per la
  catena listeners_lock/new_listener, anche le nuove connessioni SSE.
  Fix: pop del messaggio sotto lock, yield fuori dal blocco with.
- [x] R4  app/utils/events.py:101-105 - il ramo heartbeat non aggiornava
  last_active: un listener connesso ma idle veniva prunato come stale
  dopo 120 s mentre riceveva ancora heartbeat (schermata viva a video ma
  senza piu NESSUN evento). FIX via ristrutturazione R3 (il loop dei
  poll aggiorna last_active a ogni giro) + regression test in
  test_events.py (HEARTBEAT_INTERVAL ora costante di modulo).
- [x] R5  app/api/parties.py - create (:120), create-empty (:145),
  delete (:168), duplicate (:178) e template CRUD (:37,:63,:101,:238)
  NON hanno require_admin: un operatore loggato puo cancellare una festa
  o sovrascrivere template via API diretta (il blocco esiste solo nel
  frontend). Fix: require_admin su tutte le rotte mutanti
  feste/template; le GET di lettura restano accessibili (menu login).

### R-MEDIUM - dopo gli HIGH

- [x] R6  app/database/connection.py:425-429 - _ensure_party_db_exists
  gira PRIMA del check is_deleting e fuori da _lifecycle_lock: durante
  una delete una richiesta concorrente ricrea il DB (schema, operatori,
  prodotti default) e il file risorge; a delete finita, un GET col nome
  cancellato ricrea una festa vuota. Fix: check is_deleting prima della
  ensure + _lifecycle_lock attorno a creazione/migrazioni, e skip delle
  migration gia fatte (set per-processo come _checked_paths).
- [x] R7  app/services/settings_service.py:76,92 - get_device_settings e
  update_device_setting usano sqlite3.connect nudo (nessun busy_timeout
  esplicito, no WAL) e la READ esegue CREATE TABLE IF NOT EXISTS ad ogni
  chiamata; sta nel percorso di ogni checkout (metodo di default) e di
  ogni beacon (2 s). Un lock templates prolungato puo far fallire il
  checkout con OperationalError. Fix: un solo pattern connessione (WAL +
  busy_timeout), CREATE solo all-iniziazione, cache breve TTL.
- [ ] R8  app/api/cart.py:55-76,:95-112 + orders.py:55-131 - carrello nel
  cookie di sessione: due richieste concorrenti dallo stesso client =
  last-writer-wins (un add puo sparire, o resuscitare cose gia vendute).
  Fix minimale: serializzazione per-sessione delle mutazioni carrello.
- [ ] R9  app/services/order_service.py:397-406 - record_cash_count
  legge la cassa attesa e poi inserisce in due transazioni separate: un
  checkout in mezzo altera per sempre expected_cash della chiusura
  cassa. Fix: BEGIN IMMEDIATE attorno a SUM+INSERT su una sola
  connessione PartyDatabase.
- [ ] R10 app/services/auth_service.py:88-99 - upgrade del PIN legacy:
  SELECT, verifica, UPDATE; se un reset delladmin arriva tra read e
  write, lUpgrade riscrive lHash del PIN vecchio (che continua a
  funzionare). Fix: UPDATE condizionale WHERE id=? AND pin_hash=vecchio.
- [ ] R11 app/services/backup_service.py (scheduler) - snapshot manuale e
  schedulato possono sovrapporsi: stesso .tmp same-second, prune che
  cancella un vacuum in corso, rename su dest non vuota, tick non
  atomico. Fix: run_snapshots sotto un lock dedicato; prune salta i
  .tmp modificati da pochi minuti.
- [ ] R12 app/services/product_service.py:472-574 - import CSV: una sola
  transazione per tutto il file (lock oltre 10 s = la cassa si blocca) +
  get-or-create per SELECT su colonne UNIQUE = IntegrityError e rollback
  completo. Fix: commit a batch + INSERT OR IGNORE con re-SELECT nelle
  lookup (sezioni/sottosezioni/tag).
- [ ] R13 app/services/order_service.py:89-102 - overselling: MAX(0,
  stock-?) non fa andare lo stock in negativo ma REGISTRA entrambe le

  Fix: WHERE stock_count come guardia + esito venduto a 0 quando
  rowcount 0 (rifiuto con messaggio, no clamp silenzioso).

## V - VPN Tailscale / Netbird: consigli (piu avanti, come richiesto)

Non implemento feature adesso. Verdetto di design 2026-10-25:

- Cosa risolvono le VPN overlay (Tailscale, Netbird): connessione
  remota fuori dalla LAN (seconda sede, casa, supporto a distanza) con
  IP o nomi stabili; niente port-forwarding; crittografia inclusa. Per
  POSziona il modello giusto e: server e laptop dentro lo stesso
  tailnet, operatore copia-incolla una URL (recipe C5 in
  docs/connection.md la copre gia end-to-end con --server-url o menu).
- Cosa NON risolvono: la discovery LAN via UDP broadcast NON attraversa
  un overlay: dentro il tunnel circola solo unicast; la discovery
  automatica resta un affare della LAN Wi-Fi locale, sul VPN si usa la
  URL copiata o memorizzata. In pratica la VPN sostituisce (non
  aggiunge) la discovery.
- Tailscale vs Netbird:
  - Tailscale: il piu semplice; MagicDNS fornisce nomi stabili tipo
    http://cassa-1:5000/ senza IP; account cloud (oppure control-plane
    self-hosted con Headscale, un po piu complicato). Va bene per
    personale non-IT.
  - Netbird: open-source, self-hosting piu agevole; adatto se non si
    vuole un account cloud.
  - Consiglio: Tailscale se il cloud non spaventa, Netbird se
    self-host e requisito. Nessuno dei due richiede modifiche al
    codice POSziona: basta la URL (gia coperto dal C5).
- Raccomandazione: prima completare la verifica live LAN (checklist
  C6); poi, solo se emerge davvero il caso duso remoto, un documento
  dedicato docs/vpn.md con la recipe fatta bene per Tailscale e una
  per Netbird. Nessun lavoro di codice previsto.
